# Auto-Blindaje — WKH-144 (settle re-verify fail-CLOSED en mainnet)

### [2026-07-06] Wave 1 — Biome format en test nuevo (multi-line object)
- **Error**: `npm run lint` (biome) falló con 1 error de formato en `settle-verifier.test.ts`: un `new HttpRequestError({ url: ..., status: 503 })` inline que biome quería en multi-línea.
- **Causa raíz**: escribí el objeto de argumentos en una sola línea; biome fuerza multi-línea cuando el objeto supera el ancho de impresión.
- **Fix**: `./node_modules/.bin/biome check --write <file>` (autofix). Corrió directo por node_modules porque el proxy rtk reescribía `biome`/`npm` y no encontraba el ejecutable.
- **Aplicar en**: cualquier test nuevo con objetos literales largos — dejar que biome formatee (`--write`) antes de correr el lint gate, y usar el binario de `node_modules/.bin` si el proxy interfiere.

### [2026-07-06] FIX-PACK — fail-open latente FUERA del verifier (MNR-1)
- **Error**: el fix base cerró el fail-open SOLO en el return principal de `verifySettledTx` (mainnet `-mainnet` → fail-CLOSED). Pero AR+CR encontraron 2 fallbacks que hardcodeaban `{ ok: true }` network-agnostic y reabrían la MISMA vuln en mainnet: (a) el `catch` del re-verify inbound en `x402.ts` (un throw en el try — ej. `BigInt(requiredAmount)` malformado — grantaba acceso ciego), y (b) el `return { ok: true }` de `verifyDefaultChainSettle` cuando el bundle no resuelve.
- **Causa raíz**: pensar el fail-closed como una propiedad de UN return point en vez de una propiedad de TODOS los caminos "no pude verificar" del money-path. Los `catch` defensivos que asumen "el verifier nunca throwea" son fail-open latentes: si algo cambia y throwea, el literal `{ ok: true }` grantea con dinero real.
- **Fix**: exportar el choke-point `rpcUnavailableResult(chainKey)` desde `settle-verifier.ts` y reusarlo en AMBOS fallbacks. En `verifyDefaultChainSettle`, gate por `chainKey` cuando existe (mainnet fail-CLOSED / testnet fail-OPEN); si `getDefaultChainKey()` es null, no se puede clasificar → fail-OPEN histórico. En el `catch` de `x402.ts`, `chainKey` ya estaba en scope (declarado en el handler, narrowed a `ChainKey` por el guard `if (!chainKey) return 500`) — se obtiene de la MISMA var que usa `verifySettledTx` arriba. Testnet byte-idéntico en los dos.
- **Aplicar en**: el fail-closed de mainnet debe cubrir TODOS los fallbacks del verifier en TODOS los consumidores, no solo el return principal. Auditar cada `catch`/rama de error del money-path por literales `{ ok: true }` / `{ valid: true }` / `{ settled: true }` network-agnostic. **Los 5 consumidores reales del verifier**: `x402.ts` (re-verify inbound, grant-access), `compose.ts`, `fee-split.ts`, `fee-charge.ts`, `payment-intent.ts` (settle downstream vía `verifyDefaultChainSettle`). Estos 4 últimos ya gatean bien en `!ok`; el gap estaba en el `catch` de x402 y en el fallback de bundle-unresolved. NIT-3 (log "trusting facilitator" engañoso antes del block en fee-split/compose) queda deferido a follow-up (Scope OUT).
