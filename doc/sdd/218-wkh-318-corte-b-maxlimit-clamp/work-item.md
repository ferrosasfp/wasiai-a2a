# Work Item — [WKH-318 corte B] El over-fetch de `/discover` supera el techo que el registry declara y el catálogo público cae de 23 a 3 agentes en silencio

## Resumen
`resolveUpstreamFetchLimit()` manda siempre un over-fetch de 200 (o `max(pageLimit, DISCOVERY_UPSTREAM_FETCH_LIMIT)`) a cada registry cuando el caller pasa `limit`, sin mirar si ese registry declaró un techo propio. El registry `wasiai` acepta hasta 100 y devuelve `400` sobre 101+; hoy ese `400` tumba la fuente entera. Medido en prod (2026-08-04): `GET /discover?limit=N` para cualquier `N` devuelve **3 de 23 agentes** (sólo los self-published de Chaski sobreviven). Esta HU cierra el **corte B (W3)** que `WKH-318` (corte A, `doc/sdd/215-wkh-318-discover-limit-colapsa-registro-federado/`) dejó explícitamente pendiente: clampear el over-fetch al `maxLimit` que el registry ya puede declarar en su schema. Afecta directamente el pool de `/compose` que hidrata `payment.chain` (money-path).

3. **El campo para el techo YA EXISTE y NADIE LO LEE** — `src/types/index.ts:130-168`, `RegistrySchema.discovery.maxLimit?: number` (líneas 145-160). ## Acceptance Criteria (EARS)

- **AC-1**: WHEN un registry declara `schema.discovery.maxLimit` Y el caller manda `limit` a `/discover`, the system SHALL enviar a ese registry un `limitParam` que nunca exceda el `maxLimit` declarado, sin importar el valor de `limit` del caller ni el over-fetch configurado.
- **AC-2**: WHILE un registry NO declara `schema.discovery.maxLimit`, the system SHALL preservar el comportamiento actual byte-idéntico (`resolveUpstreamFetchLimit` sin clamp) — cero regresión para registries sin el campo.
- **AC-3**: WHEN el `limitParam` efectivamente enviado a un registry es el `maxLimit` clampeado Y la página vuelve llena sin evidencia de cursor, the system SHALL reportar esa fuente como `truncated`/`page_full` (nunca `http_error`/`failed` por el motivo que hoy la tumba).
- **AC-4**: IF el registry `wasiai` recibe un `limitParam` <= 100 (su techo real, medido), THEN the system SHALL NO recibir `400` de ese registry por este motivo — evidencia: request real contra `https://wasiai-v2.vercel.app/api/v1/capabilities` con el límite clampeado.
- **AC-5**: WHEN `/compose` resuelve un step por slug usando `resolveComposeAgentPoolLimit()` contra el registry `wasiai` post-fix, the system SHALL obtener el pool completo de agentes federados activos de ese registry (no sólo los 3 self-published) — medido, no asumido: comparar el tamaño del pool antes/después del fix con el mismo registry real o un mock que replique su techo de 100.
- **AC-6**: WHEN la migración de datos setea `schema.discovery.maxLimit = 100` para la fila `id = 'wasiai'` en `registries` (bdwv), the system SHALL, desde ese momento, aplicar el clamp de AC-1 a ese registry específico sin requerir ningún cambio de código adicional.
- **AC-7**: WHERE el clamp reduce el over-fetch efectivo por debajo de lo que `resolveComposeAgentPoolLimit()` esperaba (piso histórico 50, hoy potencialmente 100 para `wasiai`), the system SHALL preservar la garantía de WKH-189/BLQ-BAJO-1 (el pool de `/compose` sigue siendo superconjunto de lo que `main` traía antes del over-fetch) — con una sola fuente contribuyente esto se sostiene por construcción (`discovery-fetch-limit.ts:77-105`); si esta HU introduce un segundo registry con `maxLimit` propio, el Architect debe re-verificar la precondición documentada ahí antes de cerrar F2.

## Decisiones técnicas (DT-N)
- **DT-1**: el clamp vive DENTRO de `queryRegistry` (un solo choke-point), no en cada call-site (`compose.ts`/`orchestrate.ts`/MCP tool) — así todos los consumidores lo heredan automáticamente sin duplicar lógica, siguiendo el mismo patrón de módulo-leaf ya establecido para `resolveUpstreamFetchLimit`/`resolveComposeAgentPoolLimit`.
- **DT-2**: `min(over-fetch, maxLimit)` en vez de "usar `maxLimit` como el over-fetch fijo" — preserva la propiedad monótona de `resolveUpstreamFetchLimit` (si el caller pide más que el techo declarado, igual no puede superarlo, pero nunca se manda MENOS de lo que el registry acepta si el over-fetch por defecto ya es menor).
- **DT-3**: la migración de datos reusa el patrón exacto de la migración de `nextCursorPath` de WKH-318 corte A (mismo archivo target `registries`, mismo `jsonb_set` aditivo sobre `schema->'discovery'`, mismo guard `WHERE id = 'wasiai' AND schema -> 'discovery' IS NOT NULL`, misma restricción "SOLO bdwv") — no reinventar el mecanismo.
- **DT-4**: el "segundo defecto" (observabilidad 400 vs caído) se declara explícitamente FUERA en vez de simplemente omitirse — para que quede trazable como decisión y no como olvido (mismo criterio que D-1/B-3 de WKH-318).
